Dedicated Interconnect Networking

What is it?

Physical layer-2 connection between your on-premises network and Google's network, bypassing the public internet entirely.

↩ click to reveal details

✅ Best Fit
High-throughput (10–100 Gbps), low-latency workloads; large-scale DB replication; production hybrid architectures requiring private IPs.
❌ Not a Good Fit
Locations without Google colocation facilities; low-bandwidth or cost-sensitive dev/test workloads.
⚖ Key Trade-off
Highest performance and lowest latency, but requires colocation agreement, higher cost, and longer provisioning lead time.
💰 Cost / Security
Deploy two connections in different metro areas for 99.99% availability. Traffic never traverses the public internet, reducing exfiltration risk.
💡 Exam Scenario
A 4 TB database replicates to GCP with large frequent updates and requires private address space communication.
Google Cloud Dedicated Interconnect — high bandwidth, low latency, private connectivity.
Partner Interconnect Networking

What is it?

Connectivity to GCP through a supported service provider's network when a direct physical connection to a Google colocation facility is not possible.

↩ click to reveal details

✅ Best Fit
Locations not near a Google colocation facility; lower bandwidth needs than Dedicated Interconnect (50 Mbps to 10 Gbps).
❌ Not a Good Fit
When 10–100 Gbps throughput is required and a Google colocation facility is accessible — use Dedicated Interconnect instead.
⚖ Key Trade-off
More accessible than Dedicated Interconnect but adds a third-party provider dependency and slightly higher latency.
💰 Cost / Security
Still private — traffic goes through the partner network, not the public internet. Validate provider SLAs match your availability targets.
💡 Exam Scenario
A company needs private hybrid connectivity but is not located near a Google POP and needs 1 Gbps.
Partner Interconnect via a supported service provider.
Global External HTTP(S) Load Balancer Networking

What is it?

Google's globally distributed HTTP/HTTPS load balancer with URL-map path routing, SSL offload, and anycast frontend IP.

↩ click to reveal details

✅ Best Fit
Global web apps needing path-based routing, multi-region deployments, SSL termination at the edge, and Cloud CDN integration.
❌ Not a Good Fit
TCP/UDP apps (use TCP/SSL Proxy LB or Network LB); purely internal traffic (use Internal HTTP(S) LB).
⚖ Key Trade-off
Massive global scale and sophisticated routing vs. complexity in URL map configuration.
💰 Cost / Security
Attach Cloud Armor WAF policies to the backend service. Enable Cloud CDN to reduce backend load and egress cost.
💡 Exam Scenario
You need global path-based routing with end-to-end encryption following Google best practices.
Global External HTTPS Load Balancer with URL Maps and managed SSL certificates.
Internal HTTP(S) Load Balancer Networking

What is it?

Managed HTTP/HTTPS load balancer that distributes traffic to backends within a VPC using private internal IP addresses only.

↩ click to reveal details

✅ Best Fit
Microservices communication within a VPC or Shared VPC; internal APIs that must never be reachable from the internet.
❌ Not a Good Fit
Public-facing traffic; cross-region internal traffic (use global internal HTTP(S) LB for that).
⚖ Key Trade-off
Keeps traffic entirely internal (no public exposure), but only accessible within the VPC or connected on-premises networks.
💰 Cost / Security
No public IP means no direct internet attack surface. Use IAM and firewall rules to further restrict which services can reach the LB.
💡 Exam Scenario
Backend microservices in a VPC must be load-balanced internally without any public internet exposure.
Internal HTTP(S) Load Balancer using private IP within the VPC.
VPC Firewall Rules Networking

What is it?

Stateful ingress/egress rules applied to VPC instances, evaluated by priority number (lower number = higher priority, evaluated first).

↩ click to reveal details

✅ Best Fit
Controlling traffic between tiers in a VPC; restricting external access; enforcing egress policies without public IPs.
❌ Not a Good Fit
Cross-project perimeter control (use VPC Service Controls); layer-7 traffic inspection (use a third-party NGFW or Cloud IDS).
⚖ Key Trade-off
Simple and flexible tag-based targeting works well with autoscaling, but rules are not layer-7 aware.
💰 Cost / Security
Use network tags over CIDR ranges for autoscaling compatibility. Default-deny everything; allow only required explicit flows.
💡 Exam Scenario
A 3-tier VPC must allow web→API and API→DB traffic but block web→DB. Instances autoscale so no static IPs.
Add network tags to each tier and create ingress firewall rules scoped to those tags.
Cloud NAT Networking

What is it?

Managed network address translation service that allows instances with only private IPs to initiate outbound connections to the internet.

↩ click to reveal details

✅ Best Fit
Private GKE clusters or VMs that need to download packages or reach external APIs without having public IPs assigned.
❌ Not a Good Fit
Inbound internet connections (NAT is outbound only); use public IPs or load balancers when inbound reach is also required.
⚖ Key Trade-off
Security benefit of no public IPs on instances vs. no direct inbound internet connectivity.
💰 Cost / Security
Scope NAT to specific subnets — do not apply it org-wide unnecessarily. Monitor port allocation metrics to avoid SNAT port exhaustion under high connection loads.
💡 Exam Scenario
A subnet's VMs have only private IPs and need to download OS packages from the internet.
Configure Cloud NAT on the VPC, scoped to that subnet.
Shared VPC Networking

What is it?

Architecture where one host project owns and manages the VPC, and multiple service projects share it for compute workloads.

↩ click to reveal details

✅ Best Fit
Large organizations needing to separate network administration from compute workload ownership across teams.
❌ Not a Good Fit
Single-project setups or small teams where separation adds unnecessary overhead.
⚖ Key Trade-off
Clean separation of duties (network vs. workload teams) vs. added governance and dependency on the host project.
💰 Cost / Security
Assign Network Admin to the networking team in the host project. Dev teams get Compute Admin only in service projects — they never see host network resources.
💡 Exam Scenario
A networking team must manage all VPC resources. A dev team needs Compute Admin but must not access network config or sensitive VM data.
Shared VPC — host project owned by the networking team; dev team works in a service project with Compute Admin only.
VPC Network Peering Networking

What is it?

Private, low-latency connectivity between two VPC networks across projects or organizations using Google's internal network — no overlapping CIDRs allowed.

↩ click to reveal details

✅ Best Fit
Internal connectivity between separate VPCs in the same or different organizations where IP ranges do not overlap and transitive routing is not needed.
❌ Not a Good Fit
Overlapping CIDR ranges (use Cloud VPN + NAT instead); when transitive routing is needed (peering is non-transitive).
⚖ Key Trade-off
Simplest private multi-VPC connectivity with low latency and no VPN overhead, but strictly non-transitive.
💰 Cost / Security
No extra charge for peering itself. IAM policies still apply per project. Use firewall tags to enforce least-privilege between peered networks.
💡 Exam Scenario
Two VPCs in separate organizations with non-overlapping subnets need high-throughput, low-latency private communication.
VPC Network Peering — provides internal Google routing without public internet traversal.
VPC Service Controls Networking

What is it?

Security perimeters around GCP API services (Cloud Storage, BigQuery, etc.) that restrict access regardless of IAM permissions, preventing data exfiltration.

↩ click to reveal details

✅ Best Fit
Protecting sensitive data from exfiltration by insiders or compromised code; enforcing that GCP APIs are only accessible from specific networks or identities.
❌ Not a Good Fit
Simple IAM-only use cases without sensitive data; services not yet covered by VPC Service Controls support list.
⚖ Key Trade-off
Strong perimeter-based exfiltration protection, but requires careful access level design to avoid accidentally blocking legitimate workflows.
💰 Cost / Security
Combine with access levels scoped to corporate CIDR ranges. Audit Denied access logs to catch misconfigurations early.
💡 Exam Scenario
Data analysts have IAM access to Cloud Storage buckets but must not be able to download data from outside the office network.
VPC Service Controls perimeter with an access level limited to the office network CIDR.
Private Google Access Networking

What is it?

Subnet-level configuration that lets VM instances with only internal IPs reach Google APIs and services (Cloud Storage, BigQuery, etc.) without a public IP.

↩ click to reveal details

✅ Best Fit
VMs with no external IP that need to call Google APIs; required when using Cloud NAT is not sufficient for API access.
❌ Not a Good Fit
Access to non-Google external services — use Cloud NAT for that; not a substitute for VPC Service Controls perimeter enforcement.
⚖ Key Trade-off
Enables Google API access from private VMs at no extra cost, but only covers Google APIs — not arbitrary internet destinations.
💰 Cost / Security
Enable per subnet. Combine with VPC Service Controls for full exfiltration protection. Does not expose VMs to inbound internet traffic.
💡 Exam Scenario
A VM with no public IP must upload files to Cloud Storage in a secured environment with no internet access.
Enable Private Google Access on the subnet — the VM can reach Cloud Storage via internal routes.
Serverless VPC Access Networking

What is it?

Connector that allows serverless runtimes (Cloud Run, App Engine Standard, Cloud Functions) to reach resources inside a VPC using internal IPs.

↩ click to reveal details

✅ Best Fit
App Engine Standard or Cloud Run services that need to connect to on-premises databases via Cloud VPN, or to VPC-internal services.
❌ Not a Good Fit
Workloads already running inside a VPC (GCE, GKE) — they are already on the VPC; no connector needed.
⚖ Key Trade-off
Bridges serverless isolation to VPC connectivity, but adds a connector resource with its own scaling and cost.
💰 Cost / Security
Size the connector throughput to match traffic. The connector itself has an IP in your VPC — apply firewall rules to limit what it can reach.
💡 Exam Scenario
An App Engine Standard app must connect to an on-premises database via an existing Cloud VPN tunnel.
Configure Serverless VPC Access connector — App Engine Standard uses it to route traffic through the VPC and on to on-premises.
Cloud CDN Networking

What is it?

Google's globally distributed content delivery network, integrated with the External HTTP(S) Load Balancer to cache content at edge POPs worldwide.

↩ click to reveal details

✅ Best Fit
Static assets, media streaming, public APIs with cacheable responses, and global user bases needing low latency reads.
❌ Not a Good Fit
Dynamic fully personalized content that must not be cached; internal-only traffic with no global reach requirement.
⚖ Key Trade-off
Significant latency reduction and origin offload vs. cache invalidation complexity for frequently updated content.
💰 Cost / Security
Use signed URLs or signed cookies to protect private content behind CDN. Carefully set Cache-Control headers to avoid caching sensitive responses.
💡 Exam Scenario
A global media platform wants to reduce latency for users worldwide and lower origin server load.
Enable Cloud CDN on the backend service of the Global HTTPS Load Balancer.
Identity-Aware Proxy (IAP) TCP Tunneling Networking

What is it?

Google service that enforces identity and context-based access to internal VMs via SSH/RDP tunnels without requiring public IPs or a bastion host.

↩ click to reveal details

✅ Best Fit
SSH access to private VMs from corporate users without a VPN or bastion; identity-controlled admin access enforced at the Google level.
❌ Not a Good Fit
High-throughput application traffic (IAP is for admin tunneling, not data paths); automated on-premises-initiated connections.
⚖ Key Trade-off
More secure and auditable than bastion hosts, but requires IAP-secured Tunnel User IAM role and the gcloud CLI on the client side.
💰 Cost / Security
Grant only the roles/iap.tunnelResourceAccessor role to specific identities. Combine with OS Login for full identity-controlled SSH without managing SSH keys.
💡 Exam Scenario
Instances have no public IPs. An engineer must SSH in without violating the no-public-IP security requirement.
Configure IAP TCP tunneling and use gcloud compute ssh with the --tunnel-through-iap flag.
Cloud DNS Networking

What is it?

Scalable, reliable managed DNS service running on Google's infrastructure, supporting public and private zones.

↩ click to reveal details

✅ Best Fit
Hosting public DNS zones for domains; private zones for internal GCP service discovery; DNS peering between VPCs; hybrid on-premises DNS resolution.
❌ Not a Good Fit
Application-level service discovery within Kubernetes (use kube-dns / Cloud DNS for GKE); sub-millisecond DNS caching within a single VM.
⚖ Key Trade-off
Fully managed with 100% SLA and global anycast, but DNS propagation still has TTL-based delays for changes.
💰 Cost / Security
Use private zones to keep internal service names off the public internet. DNSSEC can be enabled on public zones to prevent spoofing.
💡 Exam Scenario
Internal GCP services must resolve each other by name without exposing those names publicly.
Create a Cloud DNS private zone scoped to the VPC.
