Cloud SQL Databases

What is it?

Fully managed relational database service for MySQL, PostgreSQL, and SQL Server workloads.

↩ click to reveal details

✅ Best Fit
Traditional relational applications; transactional systems with moderate scale; lift-and-shift apps already built on MySQL, PostgreSQL, or SQL Server; applications needing ACID transactions and SQL joins.
❌ Not a Good Fit
Massive globally distributed relational workloads; petabyte-scale analytics; very high horizontal scaling requirements beyond a traditional relational managed database model.
⚖ Key Trade-off
Familiar relational database engines with low operational overhead vs. lower horizontal scalability than globally distributed or specialized database services.
💰 Cost / Security
Use high availability configuration, automated backups, and private IP connectivity where possible. Apply least-privilege IAM and database authentication controls to reduce risk.
💡 Exam Scenario
A web application built on PostgreSQL needs a managed transactional database with minimal operational burden and no major code rewrite.
Cloud SQL — it provides managed relational database capability for common transactional workloads.
Cloud Spanner Databases

What is it?

Fully managed relational database with strong consistency, horizontal scalability, and global distribution.

↩ click to reveal details

✅ Best Fit
Mission-critical global applications; relational systems needing strong consistency at very large scale; financial systems; inventory platforms; globally distributed transactional applications.
❌ Not a Good Fit
Small low-cost applications; simple local relational workloads; systems where global scale and high availability requirements do not justify the cost and complexity.
⚖ Key Trade-off
Global scale, strong consistency, and high availability vs. higher cost and more specialized architecture decisions than traditional relational databases.
💰 Cost / Security
Spanner is powerful but often more expensive than standard relational options, so use it only when the scalability and consistency requirements justify it. Protect instances with least-privilege access, encryption controls, and regional placement aligned to compliance needs.
💡 Exam Scenario
A multinational retailer needs a single relational database that keeps inventory consistent across regions while supporting high transactional scale.
Cloud Spanner — it is designed for globally distributed relational transactions with strong consistency.
Bigtable Databases

What is it?

Fully managed NoSQL wide-column database optimized for massive scale, low-latency reads and writes, and time-series or operational analytics workloads.

↩ click to reveal details

✅ Best Fit
IoT telemetry; time-series data; clickstream ingestion; fraud signals; large-scale operational workloads requiring high throughput and low latency.
❌ Not a Good Fit
Relational data with joins; small datasets; ad hoc SQL analytics; applications needing complex multi-row transactions or traditional relational schemas.
⚖ Key Trade-off
Exceptional throughput and low latency at scale vs. no relational joins and a data model that requires access-pattern-driven design.
💰 Cost / Security
Bigtable is most efficient when designed around row-key patterns and sustained workload scale. Use IAM, private connectivity, and careful schema design to control both cost and access.
💡 Exam Scenario
A platform must ingest millions of sensor readings per second and provide fast lookups over recent and historical time-series data.
Bigtable — it is optimized for high-scale time-series and operational NoSQL workloads.
Firestore Databases

What is it?

Fully managed serverless NoSQL document database for mobile, web, and application development.

↩ click to reveal details

✅ Best Fit
User profiles; product catalogs; mobile and web application backends; hierarchical JSON-like data; apps needing flexible schema and easy developer integration.
❌ Not a Good Fit
Complex relational joins; large-scale analytical warehousing; workloads requiring full traditional SQL semantics; extreme high-throughput time-series designs better suited for Bigtable.
⚖ Key Trade-off
Flexible document model and simple application development vs. less suitability for relational workloads and large analytical processing.
💰 Cost / Security
Firestore scales automatically and reduces infrastructure management, but document reads and writes should be designed carefully to control cost. Secure collections with IAM, application-layer access controls, and least-privilege service identities.
💡 Exam Scenario
A mobile application needs a backend database for user documents and app state with flexible schema and easy scaling.
Firestore — it is the best fit for serverless document-oriented application data.
Relational OLTP Database Design Databases

What is it?

Database design pattern for transactional applications requiring structured schema, SQL queries, ACID transactions, and referential relationships.

↩ click to reveal details

✅ Best Fit
Order processing systems; customer records; ERP apps; web applications with relational business logic; moderate-scale transactional systems.
❌ Not a Good Fit
Petabyte-scale analytics, event streams, time-series ingestion, or semi-structured document-heavy mobile workloads.
⚖ Key Trade-off
Strong transactional integrity and familiar SQL modeling vs. less elasticity than specialized NoSQL or globally distributed database options.
💰 Cost / Security
Choose the simplest relational managed service that meets the scale requirement to avoid unnecessary complexity and spend. Use backups, high availability, and private access patterns to protect production data.
💡 Exam Scenario
A business system needs transactions, joins, and familiar SQL semantics, but it does not require global horizontal scale.
Use Cloud SQL for standard managed relational OLTP workloads.
Global Relational Database Design Databases

What is it?

Database architecture for relational transactions across regions with strong consistency and high availability.

↩ click to reveal details

✅ Best Fit
Financial applications; global inventory; critical transactional systems spanning multiple regions; workloads needing horizontal scalability without losing relational guarantees.
❌ Not a Good Fit
Small or local transactional applications where traditional managed relational databases are sufficient and cheaper.
⚖ Key Trade-off
Strong consistency and global scale vs. higher cost and more deliberate schema and architecture planning.
💰 Cost / Security
Only choose this design when requirements explicitly demand global consistency and scale. Ensure access controls, encryption policies, and regional compliance settings are designed at the start.
💡 Exam Scenario
An enterprise requires one globally available relational backend for mission-critical transactions across several continents.
Use Cloud Spanner for globally distributed relational database design.
Analytical Warehouse Design Databases

What is it?

Database architecture pattern optimized for large-scale read-heavy analytical queries over structured and semi-structured historical data.

↩ click to reveal details

✅ Best Fit
Business intelligence; reporting; large SQL aggregations; dashboarding; data science exploration over large datasets.
❌ Not a Good Fit
Frequent row-by-row transactions, application backends needing millisecond updates, or operational systems with heavy write concurrency.
⚖ Key Trade-off
High-performance analytics and elastic scale vs. poor fit for transactional workloads.
💰 Cost / Security
Control cost with partitioning, clustering, efficient query design, and lifecycle management. Use role-based access, views, and dataset security to restrict sensitive analytical data.
💡 Exam Scenario
Analysts need to query years of business data with large SQL aggregations and interactive reporting.
Use BigQuery for analytical warehouse design.
Time-Series NoSQL Design Databases

What is it?

Database design approach optimized for very high write throughput, low-latency reads, and access patterns centered on timestamped or key-ordered data.

↩ click to reveal details

✅ Best Fit
Sensor telemetry; monitoring data; clickstreams; financial tick feeds; large operational event storage.
❌ Not a Good Fit
Complex relational joins, ad hoc SQL-heavy analytics, or low-scale application databases with simple transactional needs.
⚖ Key Trade-off
Excellent scalability and performance for key-based access patterns vs. limited relational capabilities and the need for careful schema design.
💰 Cost / Security
Schema and row-key design drive performance and cost efficiency, so poor modeling can create hotspots and waste resources. Restrict access through IAM and isolate production data paths with private networking where appropriate.
💡 Exam Scenario
A system must store and retrieve massive volumes of timestamped device data with very high ingestion throughput.
Use Bigtable for time-series NoSQL design.
Document Database Design Databases

What is it?

Database architecture based on flexible JSON-like documents instead of fixed relational tables.

↩ click to reveal details

✅ Best Fit
Mobile and web applications; rapidly evolving schemas; user-centric data; content metadata; application state and profile storage.
❌ Not a Good Fit
Heavily relational systems requiring many joins and strict normalized schemas, or high-scale analytical warehousing.
⚖ Key Trade-off
Developer agility and schema flexibility vs. weaker fit for complex relational workloads.
💰 Cost / Security
Flexible models can simplify development, but document access patterns should be designed to avoid excessive read and write costs. Apply least-privilege access and avoid exposing broad document collections unnecessarily.
💡 Exam Scenario
A startup is building a mobile app backend and expects the schema to evolve frequently as product features change.
Use Firestore for document database design.
Transactional vs Analytical Separation Databases

What is it?

Architecture principle that separates operational transactional databases from analytical reporting systems to optimize each workload independently.

↩ click to reveal details

✅ Best Fit
Businesses running production applications and also needing large-scale reporting or BI on the same business data.
❌ Not a Good Fit
Trying to force one database to perform both heavy OLTP and heavy OLAP equally well.
⚖ Key Trade-off
Better performance and scalability for each workload type vs. added architecture for data movement and synchronization.
💰 Cost / Security
Separating OLTP and OLAP avoids overloading transactional systems and often lowers operational risk. Secure both environments independently and control what production data is replicated into analytics systems.
💡 Exam Scenario
A company’s transactional application slows down whenever analysts run large reporting queries against the same database.
Separate the workloads by using Cloud SQL or Spanner for transactions and BigQuery for analytics.
Database Selection by Consistency and Scale Databases

What is it?

Architecture decision process that chooses databases based on required consistency, schema model, query style, scaling behavior, and workload pattern.

↩ click to reveal details

✅ Best Fit
Exam questions where several database options seem possible and the right answer depends on transaction semantics, global scale, throughput, or schema flexibility.
❌ Not a Good Fit
Choosing a database based only on familiarity or brand preference rather than workload requirements.
⚖ Key Trade-off
Correct database selection improves performance, resilience, and cost efficiency; poor selection causes operational pain and expensive redesign later.
💰 Cost / Security
Pick the simplest database that satisfies the stated need, then apply backups, encryption, IAM, and network controls appropriate to that service. Overengineering database choice often increases both cost and complexity.
💡 Exam Scenario
One workload needs petabyte analytics, another needs standard relational transactions, another needs global consistency, another needs time-series throughput, and another needs flexible mobile app documents.
Use BigQuery for analytics, Cloud SQL for standard relational OLTP, Spanner for global relational scale, Bigtable for high-throughput time-series NoSQL, and Firestore for document-oriented application data.
High Availability for Databases Databases

What is it?

Design approach that removes database single points of failure through replication, failover configuration, and managed resilience features.

↩ click to reveal details

✅ Best Fit
Production systems where downtime has business impact and the database is critical to application availability.
❌ Not a Good Fit
Assuming backups alone provide high availability, or deploying a single-instance database for a critical workload without failover planning.
⚖ Key Trade-off
Better uptime and resilience vs. higher cost and potentially more configuration complexity.
💰 Cost / Security
Enable managed high availability features where supported and combine them with backups because HA does not replace restore protection. Restrict administrative access and monitor failover behavior to avoid operational surprises.
💡 Exam Scenario
A production transactional database must remain available during instance failure with minimal manual intervention.
Use a high-availability database configuration rather than relying only on backups or a single-instance deployment.
Database Migration with Minimal Refactoring Databases

What is it?

Migration approach that moves existing databases to the closest managed target that preserves application compatibility and minimizes code change.

↩ click to reveal details

✅ Best Fit
Legacy applications, short migration timelines, risk-sensitive environments, and systems already tied closely to a known relational engine.
❌ Not a Good Fit
Greenfield applications that could benefit more from redesigning for cloud-native database models.
⚖ Key Trade-off
Faster, lower-risk migration vs. potentially missing long-term optimization opportunities from deeper redesign.
💰 Cost / Security
Choosing a compatible managed target lowers migration risk and often reduces operations burden immediately. Preserve backups, access controls, encryption, and network restrictions during and after the migration.
💡 Exam Scenario
An application using MySQL must move quickly to Google Cloud with minimal database engine changes.
Use Cloud SQL as the managed relational target for minimal-refactoring migration.
