Primitive Roles Security & IAM

What is it?

Broad legacy project-level IAM roles such as Owner, Editor, and Viewer that grant large sets of permissions across many services.

↩ click to reveal details

✅ Best Fit
Very limited temporary use in simple non-production environments where broad access is acceptable and risk is low.
❌ Not a Good Fit
Production systems, regulated environments, and organizations requiring least privilege or separation of duties.
⚖ Key Trade-off
Easy to assign and understand vs. excessive access that increases security and operational risk.
💰 Cost / Security
Avoid primitive roles for routine access because they often grant much more permission than necessary. Replace them with predefined or custom roles tailored to job function.
💡 Exam Scenario
An administrator wants to give a developer easy access to one workload in production and is considering the Editor role.
Do not use a primitive role; grant a narrower predefined or custom role instead.
Custom Roles Security & IAM

What is it?

User-defined IAM roles that include a tailored set of permissions when predefined roles are too broad or do not match job requirements precisely.

↩ click to reveal details

✅ Best Fit
Enterprises with strict least-privilege requirements, unique job responsibilities, or compliance constraints.
❌ Not a Good Fit
Cases where an existing predefined role already meets the requirement cleanly and simply.
⚖ Key Trade-off
Better permission precision and compliance alignment vs. more administrative effort to design, test, and maintain role definitions.
💰 Cost / Security
Use custom roles only when predefined roles are not sufficient, and review them regularly as services evolve. Poorly designed custom roles can become difficult to maintain over time.
💡 Exam Scenario
A compliance-sensitive team needs a very specific permission set that cannot be met by any single predefined role without overgranting access.
Create a custom role that contains only the required permissions.
Service Accounts Security & IAM

What is it?

Identities used by applications, VMs, and managed services to authenticate and authorize access to Google Cloud APIs and resources.

↩ click to reveal details

✅ Best Fit
Workloads that need non-human access to cloud resources, such as VMs accessing storage, applications calling APIs, or jobs reading from databases.
❌ Not a Good Fit
Sharing one highly privileged service account across unrelated workloads or using user identities for automated machine-to-machine access.
⚖ Key Trade-off
Secure workload identity and automation vs. risk if accounts are overprivileged or credentials are mishandled.
💰 Cost / Security
Create separate service accounts for separate workloads and grant each only the minimum permissions required. Avoid long-lived keys whenever possible and prefer attached identities or short-lived credentials.
💡 Exam Scenario
A Compute Engine instance needs to read objects from one bucket and publish messages to one Pub/Sub topic, but nothing more.
Attach a dedicated service account with only the required Storage and Pub/Sub permissions.
Service Account Key Avoidance Security & IAM

What is it?

Security practice of avoiding downloadable long-lived service account keys and instead using attached identities, metadata-based credentials, or short-lived token methods.

↩ click to reveal details

✅ Best Fit
Modern cloud-native workloads, managed services, and security-conscious environments seeking to reduce credential leakage risk.
❌ Not a Good Fit
Workflows that unnecessarily export private keys to local machines, source repositories, or unmanaged systems.
⚖ Key Trade-off
Much lower credential exposure risk vs. requiring better identity architecture and integration design.
💰 Cost / Security
Long-lived keys are hard to rotate and easy to leak, so avoid them unless absolutely necessary. Prefer built-in workload identity patterns and controlled credential issuance methods.
💡 Exam Scenario
A team wants an application running on Google Cloud to access other Google Cloud services securely without storing secrets on disk.
Use the workload’s attached service account identity instead of creating and distributing service account keys.
Least Privilege for Workloads Security & IAM

What is it?

Security principle that workload identities should receive only the permissions needed for their exact runtime behavior.

↩ click to reveal details

✅ Best Fit
All production workloads, especially shared environments, regulated systems, and architectures with multiple services.
❌ Not a Good Fit
Giving service accounts project-wide editor access for convenience or granting future hypothetical permissions that are not currently required.
⚖ Key Trade-off
Stronger security and smaller blast radius vs. more detailed access analysis and role assignment work.
💰 Cost / Security
Restrict workload identities tightly because compromised services can otherwise be used to access unrelated resources. Review permissions regularly as application behavior changes.
💡 Exam Scenario
A microservice only needs read access to one dataset but was given broad access to many project resources.
Replace the broad role with the minimum dataset-specific access required.
IAM Policy Inheritance Security & IAM

What is it?

IAM model where permissions granted at the organization, folder, or project level are inherited by lower-level resources unless more specific conditions apply.

↩ click to reveal details

✅ Best Fit
Large organizations that need scalable access management across many projects and resources.
❌ Not a Good Fit
Granting broad access high in the hierarchy without understanding that it will flow down to many lower-level resources.
⚖ Key Trade-off
Easier centralized administration vs. higher risk of unintended permission spread if bindings are placed too broadly.
💰 Cost / Security
Apply broad permissions carefully at higher hierarchy levels because inherited access can affect many environments. Use resource-level scoping for sensitive workloads when needed.
💡 Exam Scenario
An administrator grants a group access at the project level and later discovers that many resources inherited those permissions automatically.
Review IAM inheritance and move sensitive access grants to narrower scopes where appropriate.
Separation of Duties Security & IAM

What is it?

Security and governance principle where different teams or identities are responsible for different environments or functions, such as development, production, networking, or security administration.

↩ click to reveal details

✅ Best Fit
Enterprises, regulated workloads, and organizations requiring strong governance and controlled production access.
❌ Not a Good Fit
Flat access models where the same users can administer everything across all environments without restriction.
⚖ Key Trade-off
Better governance, auditability, and risk reduction vs. more operational coordination and role design complexity.
💰 Cost / Security
Separation of duties reduces accidental or unauthorized changes to sensitive systems. Combine it with project separation and least-privilege IAM for stronger control.
💡 Exam Scenario
A company requires developers to manage dev resources but forbids them from directly changing production security settings.
Implement separation of duties with distinct roles and environment boundaries.
Cloud DLP Security & IAM

What is it?

Sensitive data discovery and protection service that can inspect, classify, mask, tokenize, or de-identify data such as PII, financial data, and confidential records.

↩ click to reveal details

✅ Best Fit
Compliance programs; data discovery; protecting customer records; redacting sensitive information in storage, logs, or pipelines.
❌ Not a Good Fit
General encryption key management, identity administration, or application authorization use cases.
⚖ Key Trade-off
Strong visibility into sensitive data and automated protection options vs. added scanning design, policy choices, and possible processing cost.
💰 Cost / Security
Use DLP to discover where regulated or sensitive data exists before applying controls or sharing datasets. Minimize exposure by masking or tokenizing data when full values are not required.
💡 Exam Scenario
An organization needs to find and de-identify personally identifiable information before sharing a dataset with analysts.
Use Cloud DLP to inspect and de-identify the sensitive data.
Data De-identification Security & IAM

What is it?

Security technique that removes, masks, tokenizes, or transforms sensitive values so data can be used with reduced privacy risk.

↩ click to reveal details

✅ Best Fit
Analytics sharing; test datasets; privacy-sensitive workflows; partial data access for teams that do not need the original values.
❌ Not a Good Fit
Cases where full original values must remain visible to all users or where encryption key management is the primary requirement.
⚖ Key Trade-off
Better privacy protection and safer data use vs. possible loss of fidelity or usefulness depending on the transformation method.
💰 Cost / Security
Choose masking, tokenization, or pseudonymization based on the business need for reversibility and analysis quality. Apply de-identification before data is broadly shared to reduce compliance risk.
💡 Exam Scenario
A business wants to share customer data internally for analytics but must not expose raw personal identifiers.
De-identify the data with Cloud DLP before sharing it.
Cloud KMS Security & IAM

What is it?

Managed encryption key management service for creating, controlling, rotating, and auditing cryptographic keys used to protect data.

↩ click to reveal details

✅ Best Fit
Centralized key management; regulatory encryption requirements; customer-managed encryption keys; workloads needing separation between data storage and key control.
❌ Not a Good Fit
Data classification, PII inspection, or user permission management use cases.
⚖ Key Trade-off
Stronger control over encryption and auditability vs. extra operational decisions around key hierarchy, rotation, and access governance.
💰 Cost / Security
Use Cloud KMS when you need control over key lifecycle, access, and auditability beyond default encryption. Limit who can use or manage keys because key access can indirectly control data access.
💡 Exam Scenario
A company must retain control over encryption keys for regulated data stored in Google Cloud services.
Use Cloud KMS to manage customer-controlled encryption keys.
CMEK Security & IAM

What is it?

Customer-Managed Encryption Keys model where Google Cloud services encrypt data using keys that the customer controls in Cloud KMS.

↩ click to reveal details

✅ Best Fit
Regulated workloads; strict compliance requirements; enterprises needing explicit control over encryption key use and rotation.
❌ Not a Good Fit
Workloads where default Google-managed encryption is sufficient and there is no requirement for customer-controlled keys.
⚖ Key Trade-off
More control and compliance alignment vs. more responsibility for key availability, rotation, permissions, and operational planning.
💰 Cost / Security
CMEK can help satisfy regulatory and organizational key-control requirements, but incorrect key permissions or disabled keys can break workloads. Plan key lifecycle and access policies carefully.
💡 Exam Scenario
An auditor requires that the company, not just Google, controls the keys protecting stored data.
Enable CMEK using Cloud KMS for the supported services handling that data.
Key Rotation Security & IAM

What is it?

Practice of regularly replacing cryptographic keys to reduce the exposure window if a key is compromised or to meet compliance requirements.

↩ click to reveal details

✅ Best Fit
Regulated systems, long-lived encrypted data, and organizations with formal security policies.
❌ Not a Good Fit
Environments that create keys and never review or rotate them despite policy or risk requirements.
⚖ Key Trade-off
Reduced long-term key exposure vs. additional lifecycle management and change coordination.
💰 Cost / Security
Define rotation schedules that match policy and workload sensitivity. Rotation should be tested so applications continue operating correctly with new key versions.
💡 Exam Scenario
A security policy requires encryption keys protecting sensitive data to be replaced on a scheduled basis.
Use managed key rotation practices in Cloud KMS.
Compliance by Design Security & IAM

What is it?

Architecture approach where regulatory, privacy, audit, residency, and access-control requirements are designed into the system from the beginning.

↩ click to reveal details

✅ Best Fit
Healthcare, finance, government, and any workload with legal or contractual security obligations.
❌ Not a Good Fit
Building first and trying to retrofit compliance controls only after deployment or audit findings.
⚖ Key Trade-off
Better audit readiness and lower regulatory risk vs. more design constraints and documentation effort early in the project.
💰 Cost / Security
Compliance often affects region choice, IAM design, logging, retention, encryption, and data handling workflows. Early planning is usually cheaper and safer than retroactive remediation.
💡 Exam Scenario
A company must store sensitive records under strict regulatory controls and prove that access, encryption, and audit requirements are enforced.
Design the architecture around compliance requirements from the start, including IAM, logging, encryption, and controlled data handling.
Audit Logging Security & IAM

What is it?

Security logging capability that records administrative actions, access events, and system activity for accountability and forensic review.

↩ click to reveal details

✅ Best Fit
Compliance programs; incident investigations; privileged access monitoring; change tracking in production environments.
❌ Not a Good Fit
Environments that rely only on human memory or informal process for tracking sensitive actions.
⚖ Key Trade-off
Better traceability and accountability vs. more log volume and the need to manage retention and access securely.
💰 Cost / Security
Audit logs are critical for investigations and compliance evidence, but they must be protected because they reveal sensitive operational activity. Retention and export strategy should align with legal and security requirements.
💡 Exam Scenario
A security team needs to know who changed IAM permissions on a project and when the change occurred.
Use audit logging to track administrative and access activity.
Secret Separation from Code Security & IAM

What is it?

Security practice of keeping passwords, API keys, certificates, and other sensitive values outside source code and deployment artifacts.

↩ click to reveal details

✅ Best Fit
All production applications, CI/CD systems, microservices, and regulated environments.
❌ Not a Good Fit
Hardcoding secrets in repositories, VM startup scripts, container images, or notebook files.
⚖ Key Trade-off
Stronger credential protection and easier secret rotation vs. the need for runtime retrieval and secret management design.
💰 Cost / Security
Hardcoded secrets are easy to leak and hard to rotate safely. Store secrets in a dedicated secret management system and grant access only to the required workload identities.
💡 Exam Scenario
An application needs a database password, but the security team forbids storing it in source code or plaintext environment files.
Store the secret outside the codebase and grant runtime access only to the application identity.
Compliance-Aware Data Sharing Security & IAM

What is it?

Controlled approach to sharing data so that users receive only the minimum permitted information under privacy, legal, and policy requirements.

↩ click to reveal details

✅ Best Fit
Internal analytics, partner data exchange, regulated datasets, and multi-team organizations with varying access rights.
❌ Not a Good Fit
Sharing raw sensitive datasets broadly without masking, de-identification, or access minimization.
⚖ Key Trade-off
Better privacy and regulatory alignment vs. more effort in policy design, data transformation, and access review.
💰 Cost / Security
Use IAM, de-identification, and selective dataset exposure to reduce unnecessary data access. Shared datasets should be reviewed for both business usefulness and privacy risk.
💡 Exam Scenario
Analysts need access to customer behavior data, but privacy rules prohibit exposing direct personal identifiers.
Share only the permitted data and apply DLP-based de-identification where necessary.
Defense in Depth Security & IAM

What is it?

Security strategy that combines multiple independent controls such as IAM, encryption, logging, network restrictions, and data protection instead of relying on one mechanism alone.

↩ click to reveal details

✅ Best Fit
Production systems, sensitive workloads, internet-facing applications, and regulated environments.
❌ Not a Good Fit
Architectures that assume one control such as IAM alone is sufficient to address all security risks.
⚖ Key Trade-off
Stronger protection and reduced single-control failure risk vs. more architectural complexity and policy coordination.
💰 Cost / Security
Combine least privilege, service account isolation, key management, audit logging, and sensitive data protection for layered security. This approach improves resilience against mistakes, misuse, and compromise.
💡 Exam Scenario
A company wants a cloud architecture that protects sensitive workloads even if one security control is misconfigured or bypassed.
Apply defense in depth by combining IAM, encryption, logging, and data protection controls.
